# 红绿循环：规则与陷阱

## 什么算好测试

好测试**只通过公开接口观察行为**，不关心内部怎么实现。代码可以整个重写，测试不该动。

它读起来像一句话规格：

```
用户可以取消未发货的订单
```

看到测试名就知道系统有这个能力，而且重构不会让它变红——因为它压根不知道内部结构。

一个测试只验一件事。断言的期望值必须是**独立来源**：手写的字面量、从需求里抄下来的数、已知正确的样例。

## 测试写在哪

seam 是"不碰内部实现就能观察行为"的位置：HTTP 接口、模块公开函数、CLI 命令、组件 props。

规则只有一条：**用尽可能高的现有 seam，新增的越少越好。** 新增一个 seam 的代价，通常高于把测试写高一层。

不要测私有函数，不要为了好测重排模块边界。但把函数内部 new 出来的外部客户端改成参数传入是允许的——那是为了能在系统边界上 mock，不是设计决策。

spec 里的"测试落点"是缺省值，不是约束。选了不同的 seam，说一句理由，回填时覆盖它。

## 三种坏测试

### 1. 和实现耦合

```ts
// 坏：验证的是"有没有调用那个方法"，不是"用户能不能取消"
const spy = jest.spyOn(order, "setStatus");
await cancelOrder(orderId);
expect(spy).toHaveBeenCalledWith("cancelled");
```

识别方法：**重构之后行为没变，但测试红了**——说明它测的是结构。

同类的还有：测私有函数、断言调用次数、绕开接口去查数据库。

```ts
// 坏：绕过接口直接查库
await createUser({ name: "Alice" });
const row = await db.query("select * from users where name = ?", ["Alice"]);
expect(row).toBeDefined();

// 好：通过接口验证
const user = await createUser({ name: "Alice" });
expect((await getUser(user.id)).name).toBe("Alice");
```

### 2. 同义反复

期望值用和实现一样的算法算出来，于是它按构造必然通过，永远不会和代码产生分歧。

```ts
// 坏：期望值就是把实现重写了一遍
const expected = items.reduce((s, i) => s + i.price, 0);
expect(calculateTotal(items)).toBe(expected);

// 好：期望值是个独立的字面量
expect(calculateTotal([{ price: 10 }, { price: 5 }])).toBe(15);
```

快照测试容易掉进这个坑：快照如果是照当前输出生成的，它就只是在记录"现在长这样"，不是"应该长这样"。

### 3. 水平切片

先把所有测试写完，再一次性实现。

这是最隐蔽的一种，因为它看起来"很 TDD"——毕竟测试确实先写了。但它测的是**想象出来的行为**：你还没实现，就先把接口形状、错误类型、边界都定死了，然后实现被迫去迁就这些猜测。

正解是垂直切：**一个测试 → 一个实现 → 下一个测试**，每个测试是一发子弹，打出去之后根据结果再决定下一发瞄哪。

## 怎么确认"红得对"

写完结账前必做的一步，也是 TDD 最容易被糊弄的一步。

跑测试，看它失败，然后确认三件事：

1. **失败原因**是"功能不存在"（断言不成立），不是 import 失败、语法错误、测试自己写错
2. **失败位置**在断言上，不是在 setup 里
3. **失败信息**能读出"期望什么、实际什么"

如果一条测试从来没红过，它证明不了任何事——很可能它测的东西本来就不依赖你要写的代码。

## 最小实现

绿的标准是"这条测试过了"，不是"这个功能完整了"。

诱惑在于：既然知道下一条 AC 是什么，不如一起写了。别。多做的那部分没有测试保护，而且它一旦写错，你会以为问题出在已经绿了的那条上。

写死一个常量能让测试过，就先写死。下一条测试会逼你把它变成真的。这不是偷懒，这是让需求一步步驱动结构。

注意区分两种"写死"：

- **临时的**：为了过当前这条测试写死一个返回值，几条测试之内就会被真实实现替换掉。不用留标记，它活不过这个会话
- **长期的**：写死的 user_id、跳过的鉴权、用 JSON 文件冒充数据库——这些会跟着代码走很久，必须打 `// MVP-FAKE(MVP-007)` 标记

把临时的当成长期的，代码里会爬满无意义的注释；把长期的当成临时的，半年后没人知道哪里有洞。

## 依赖外部系统时

| 依赖 | 做法 |
|---|---|
| 纯逻辑 | 直接测，不 mock 任何东西 |
| 外部 API | 契约测试或录制回放 fixture；真实调用只跑一次，不进 CI |
| 数据库 | 测试库优先；否则每例自建数据、跑完清理 |
| UI / 异步 | 一条 e2e 覆盖主路径，其余在更低的 seam 上测 |
| 时间 / 随机 | 注入 fake clock，等待用带上限的轮询（≤5s） |

测试必须确定：禁 sleep、禁依赖执行顺序、禁并行不安全、禁跨用例共享状态。

一条 flaky 测试会让后面所有红灯失去意义——你分不清是代码坏了，还是测试本身在抖。

## Mock 的边界

只在**系统边界**上 mock：

- 外部 API（支付、邮件、第三方服务）
- 时间、随机数
- 数据库（优先用测试库，实在不行才 mock）
- 文件系统

不要 mock 自己的类、模块、内部协作者——那样测的是"连接方式"，不是行为。

为了好 mock 而设计接口时，用依赖注入 + 每个外部操作一个具体函数，而不是一个万能的 `fetch(endpoint, options)`。前者每个 mock 返回一种确定的形状，后者要在 mock 里写条件分支，很快就没人看得懂了。

## 循环里不该出现的动作

- 为了让测试过而改测试（除了测试本身写错了）
- 加 `sleep` / 重试 / 放宽断言
- `skip` / `only` / 注释掉
- 先写实现再补测试，然后声称走了 TDD——红证据会暴露它
- 在循环里顺手重构

## 红灯清单

出现下面任何一条，停手回看：

- 连续三条测试都一次就绿 → 你要么在测已经有的东西，要么测试没断言到点上
- 测试文件比实现文件长很多 → 可能在测实现细节
- 改一个字段名，红了十个测试 → 测试和结构耦合了
- 全绿但验收命令跑不通 → 测试跑在错误的 seam 上
