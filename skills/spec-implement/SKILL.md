# Spec Implement

按一份 spec 实现一片功能。每条验收标准一个红绿循环。

**完成的标准**：每条 AC 都有一条曾经红过、现在绿着的测试；验收命令跑得通；这两件事都能在回填产物里被复核。

## 为什么要能复核

"先写实现再补测试"不违反任何一句话——"确认它失败"是内心活动，没人看得见。

所以要两样东西：**贴出失败输出**，**测试与实现分开提交**。成本很低，但它把自证换成了物证。

证据是承重的，提交形式不是。仓库用 squash、有保护分支、或者压根不是 git，就跳过双提交，但红输出必须贴出并留进回填产物。

## 开工检查

两条线，别混：

**缺这些就停下来问**：AC 没有断言点、没有验收方式、没有"不做"的范围、共享契约不明、带判定阈值却没有判定协议、伪造范围触及不可伪造清单（支付、认证、删除、个人数据、合规）。

**自己补完再报一行**：缺落点、缺 AC 依赖顺序、缺测试目录、验收命令因为测试框架还没装而跑不起来。装测试框架属于实现范围，不算"加依赖"。

AC 里的用例名是占位，按实际 seam 写，回填时覆盖并记一行。

用户说"你看着办"，把你补的内容单列出来等一句确认再开工。

开工前**先跑一次验收命令**。它应该失败，但失败原因得是"功能没做"，不是"环境没配好"。

## 循环

开工先把 spec 状态改成 `in-progress`。

一条 AC 一个循环：

写测试 → 跑 → **贴出失败输出** → 提交 `test(SPEC-003 AC-2): <行为>`（只含测试）→ 写刚好够通过的代码 → 跑绿 → 提交 `feat(SPEC-003 AC-2): <行为>` → 下一条。

**spec 编号和 AC 编号都写进 commit message。** `spec-review` 靠它推导固定点、判成对提交——不写，下游只能来问你"这段改动从哪开始"。

全部绿之后：全量测试 + typecheck，跑验收命令并贴输出。需要整理结构的，单独一个 refactor commit。

AC 顺序按"最可能推翻结构"排，不按编号。这跟切片按"最大风险"排是两个层级，别混——大部分返工不是写错了，是结构定早了。

测试写在哪个边界、怎么写、mock 到哪一层，见 [references/tdd-loop.md](references/tdd-loop.md)。

## 边界

**自己可以做**：写测试、写实现、跑测试、按 AC 提交、按实际 seam 调整断言字段与落点、更新 spec 状态。

**必须先问**：改断言语义或期望值、删减 AC、动共享契约的已有字段、加运行时依赖、超预算、伪造范围超出 MVP spec 的清单。

伪造的东西留标记 `// MVP-FAKE(MVP-007): 写死 user_id，上线前换真登录`。

## 卡住时

**AC 本身写错了**（矛盾、不可能实现）→ 停，报告，由用户决定标 `superseded` 重写还是改 AC。改完再继续，不要边猜边写。

**超预算** → 停，报实际规模，建议拆片。

**缺一个 spec 没定的决策** → 先看可逆性：可逆的按低风险默认处理，在报告里注明；不可逆的停下来问。

遇到障碍时静默降低标准、然后汇报"已完成"，是执行 spec 最常见的失败。

## 没做完怎么说

有 AC 没达成，或实现与 spec 有出入：**状态保持 `in-progress`**，报告首行列出未达成的编号，偏差写进风险节。

记一笔就标 done，是最隐蔽的谎报——文档会留下"已合规"的记录，下一个人照着它继续做。

## 回填

spec 末尾有一张「回填」表，每条 AC 一行：测试 / 红提交 / 红输出 / 当前绿。**填满它**，缺一行不算完成。

写完在报告里附 `git diff --stat docs/specs/` 的输出——那是"表格确实被填进文件"的物证，不是产物本身。

变更记录加一行：实现了什么、和 spec 的差异在哪。

**状态留 `in-progress`**，终态由 `spec-review` 给——实现的人不该同时是宣布完成的人。

MVP spec 有伪造清单时，逐条核 `git grep -n "MVP-FAKE"` 是否至少命中一处。一行清单可能落多处标记，所以**不比总数，只比有没有**。

## 下一步

回填完不等于这片结束。交给 `spec-review`：换一个上下文，对照 spec 和仓库规范把 diff 审一遍，再核对回填表是不是真的。

审的人不改代码。
