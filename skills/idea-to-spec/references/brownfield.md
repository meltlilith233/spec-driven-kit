# 存量代码库：先测绘，再切片

新项目的切片方式在存量项目里会害人。在跑了两年的 monolith 里加"批量导出"，按功能切出"加表 / 加接口 / 加按钮"，最后会改动 40 个文件、顺手重构两个公共模块、回归大面积失败。

## 测绘清单（切片前必做）

不是通读代码，是回答五个问题：

1. **入口在哪**：这个新行为从哪个已有入口进来？没有入口，才需要新建。
2. **数据流怎么走**：从入口到落库经过哪几层、哪几个服务。
3. **可测的 seam 在哪**。seam 是"可以在这里替换实现而不改调用方"的位置——已有的接口、依赖注入点、HTTP 边界、消息队列。**优先用现有 seam，用尽可能高的那个，新增 seam 越少越好。** 新增一个 seam 的代价，通常高于把测试写高一层。
4. **现有测试覆盖到哪**：哪些行为已经有测试锁着，改动它们会红。
5. **哪些是公共契约**：被多处引用的类型、schema、工具函数。列出来，后面每片都要写进"共享契约"。

## 切片方式

- **按"行为变更 + 一个现有 seam"切**，不按功能切。一片 = 在某个 seam 上改变一个可观测行为。
- **第一片往往是 characterization test**：先用测试锁住现有行为，再改。没有这层，你无法区分"我改坏了"和"它本来就是坏的"。
- 需要的改动跨越多个 seam 时，先切一片"只搭桥不换引擎"的（expand），再切迁移片（migrate），最后切删除旧路径的（contract）。宽重构不要塞进垂直切片，它切不动。

## 写进 spec 的部分

存量项目的 spec 多两节：

- **现状**：涉及哪些已有模块、当前行为是什么、哪些测试覆盖着
- **回归风险**：这次改动可能让哪些已有行为变化，怎么验

其余模板不变。别在 spec 里写具体行号——半天后就过期了，写模块名和函数名。
