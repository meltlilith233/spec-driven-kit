# product.md：Scrum 语义下的产品文档

## 它是什么，不是什么

Scrum 只有三个工件：Product Goal、Product Backlog、Sprint Backlog。product.md 对应的是 **Product Goal 加上支撑它的上下文**。

所以它是：

- 一份**关于未来的假设**，会随着学习被改写
- 一份**取舍依据**，用来判断某个需求该不该进 backlog
- 两页以内，一次读完

它不是：

- PRD——没有详细功能描述，那是 spec 的事
- 合同——写死了就不叫敏捷了
- 宣传材料——"赋能""闭环""生态""一站式"这类词一律删掉

## 各部分怎么写

### 一句话定位

`为 <谁> 解决 <什么问题>，不同于 <现有做法>，我们 <关键差异>。`

写不出来，说明第 1 步还没问透。回去问，别硬编。

### 产品愿景

写**未来状态**，不写功能。三句话：

1. 三年后，用户的世界因为这件事变成了什么样
2. 这件事为什么值得做——对用户，不是对我们
3. 什么情况下这个愿景就不成立了（kill criteria）

第 3 条最容易被漏，也最值钱：它让团队知道什么时候该掉头，而不是硬撑半年。

> 反例：「打造一站式智能协作平台，赋能企业数字化转型。」
> 没有一个具体的用户，没有一件具体的事，无法被证伪。
>
> 正例：「让小团队在没有专职 PM 的情况下，也能在一周内把一句模糊需求变成可执行的开发任务。如果团队规模超过 50 人时这套流程反而变慢，这个产品的前提就不成立。」

### 用户画像

2-3 个，不要更多。画像越多，通常说明越没想清楚。

每个画像写这五样——这是 JTBD 的写法，不是人口统计：

- **角色与情境**：什么岗位，在什么时刻会打开这个东西
- **要完成的事**：一句动词开头的话
- **现在的凑合方案**：用什么替代品，忍受了什么
- **最痛的一环**：具体到某个动作，不是"效率低"
- **愿意付出什么**：时间？钱？改变习惯？不愿付出 = 不是真需求

再加一个**反画像**：明确谁不是目标用户，以及为什么。

> 反例：「李经理，35 岁，一线城市，注重效率，喜欢尝试新事物。」——这是简历，不是画像。
>
> 正例：「接私活的全栈开发者，客户在微信上丢来一段语音需求。现在的做法是反复听、手写笔记、再整理成待办。最痛的是需求变更时找不到当初的原始描述。愿意为此每天多花 10 分钟，但不愿意换掉现有的任务管理工具。」

注意最后半句——"不愿意换掉现有工具"这类约束，比前面所有描述都更能指导设计。

### 目标与非目标

目标 3-5 条，每条指向愿景的一部分。

非目标至少和目标一样多，格式统一为"不做 X，因为 Y"。

非目标是这份文档里性价比最高的一节。没有它，任何需求都能被论证成"这也是用户要的"。

### 成功指标

每条指标三要素：**数字 + 时间 + 测量方式**。

- 领先指标：一周内能看到变化，用来快速调整
- 滞后指标：真正关心的结果，来得慢
- 护栏指标：不能变坏的东西——延迟、成本、投诉率、人工介入次数

> 反例：「提升用户满意度」
> 正例：「上线 4 周内，完成首次完整流程的用户中 ≥40% 在 7 天内再次使用。测量方式：埋点 `flow_completed` 与 `session_start` 的留存队列。」

### 约束与假设

- **约束**：技术上必须/不能用的，合规死线，上线窗口，团队规模
- **假设**：还没验证但必须先信的东西。每条配"怎么验证、什么时候验证"

假设清单是 backlog 排序的重要输入——验证关键假设的切片应该往前排。这也是唯一能名正言顺插队的东西。

### 最大风险

只写一条，最可能致命的那条。第 1 步问过"如果失败最可能因为什么"，答案就在这。

写两条以上等于没写——因为它意味着你还没排序。

### 首个可用增量

一句话：**最小能让人用起来并给出反馈的东西是什么**。它对应第 3 步的行走骨架。

### 待定问题

列出来，每条带"谁来决定、什么时候必须定"。

假装什么都定了，是最危险的信号。一份没有待定问题的 product.md，通常不是想清楚了，而是把问题藏起来了。

## 出口检查（机械可查）

逐条打勾，每条都能由一个 agent 独立判定，不依赖"读起来感觉对不对"：

- [ ] 两页以内
- [ ] 一句话定位四个槽都填满（谁 / 什么问题 / 不同于什么 / 差异在哪）
- [ ] 没有一个空形容词（"高效""智能""无缝"要么删掉，要么换成可观测的行为）
- [ ] 每个画像都对应到至少一条非目标
- [ ] 每条指标都有数字 + 时间 + 测量方式
- [ ] 有一条 kill criteria，且指向一个可观测事件
- [ ] 待定问题都写了"谁来定、什么时候必须定"

用户能不能复述是加分项，不是门禁——在 solo 场景下这个测试恒真，考的是他的记性，不是文档的质量。

## 维护节奏

不用排期，用事件触发：

- 任何一片 spec 标 `done` 后过一遍：愿景有没有被这次实现证伪？指标口径还对不对？非目标要不要放宽？
- 出现"这个功能用户肯定会要"这类争论时，回来看非目标——它本来就是为这种争论准备的

改的时候留一行变更记录。改它不是失败，是学习。
