# Spec：先切成片，再写透

## 第一件事是切片，不是写

拿到 product.md 之后最容易犯的错，是直接开始写需求文档。先切。

### 垂直切片

一片必须**穿透所有层**，做完之后是一个能演示的完整行为。

反例（按层切）：

- 切片 1：设计数据库表结构
- 切片 2：实现 API
- 切片 3：实现前端页面

前两片做完什么都演示不了；真正的问题（层与层对不上）会憋到最后一片集中爆发。

正例（垂直切）：

- 切片 1：用户提交一句话需求，系统存下来并在列表里显示（最薄的端到端通路）
- 切片 2：提交时自动拆成 3 条任务建议
- 切片 3：用户可以编辑并确认任务建议

### 第一片：能证伪最大风险的那条通路

不要默认"最薄通路 = 第一片"。最薄通路通常是 CRUD，而最大风险往往在效果、数据或性能上。

两者不同一时，先插一个 spike 验风险（上限一次会话，产出是结论 + 证据），再补骨架。理由很简单：用确定的顺序保护一个未经验证的假设，就是瀑布。

### 粒度：事前可判的代理指标

"一次会话做得完"是事后判据，切片时用不了。用这组代替，任一项超出就先试着拆：

| 指标 | 默认阈值 |
|---|---|
| 改动文件数 | ≤ 5 |
| 净增代码（不含测试） | ≤ 400 行 |
| 验收标准条数 | ≤ 8 |
| 新增外部依赖 | 0 |
| 数据库迁移 | 0（或一个纯增列） |
| 新增环境变量 / 配置项 | 0 |

阈值按项目校准。拆不动的，在 spec 里写一句为什么，别硬拆——切太细只是多写几个标题，切太粗要返工。

开工前先让执行者报一次预算（预计改动哪些文件、预计几条 AC）。超阈值就停手回去拆，而不是做到一半才发现。

### 依赖是有向图，不是列表

每片标明"被谁阻塞"。没有阻塞的片可以立刻开工——这就是并行度的来源。

如果一片被三片阻塞，通常说明它切粗了，或者它在做集成而不是在交付能力。

## 一份 spec 的解剖

### 1. 背景（自包含）

一个新会话的执行者只读这份文件就要能开工。背景必须自带：这是什么产品、这片在整体里的位置、为什么现在做它。

不要写"如上所述""参见之前的讨论"——那些上下文在他那里不存在。

### 2. 目标 / 不做

**这条 spec 完成后，什么行为从无到有。** 一句话。

然后是"不做"：这一片明确不覆盖的范围。既是防膨胀的闸门，也是并行开发的边界线。

### 3. 用户故事

格式：`作为 <画像>，我想要 <能力>，以便 <结果>。`

- 画像不得临时发明，但**必须在 spec 内联一行复述**（`画像：接私活的全栈开发者，客户在微信丢语音需求…`，末尾注明完整定义在 product.md 哪一节）。只写"见 product.md"等于破坏自包含
- "以便"后面是用户获得的价值，不是系统行为（"以便数据被保存"是错的）
- 3-7 条。超过 7 条，这片太大

用户故事是给人和验收看的。执行者看验收标准。

### 4. 验收标准（整份文档最重要的一节）

每条 AC 必须能回答三个问题：

| 要素 | 要求 |
|---|---|
| 断言谁 | 接口路径 / 表名 / 选择器 / 日志字段 |
| 怎么断言 | 测试文件 + 用例名，或一条命令 |
| 期望值 | 字面量，不是形容词 |

**能机器断言的一律写成机器断言。** 只能人判的（视觉、文案、手感），必须写明谁判、判什么、什么算通过——不能只写"界面友好"。

```
AC-1  给定 未登录用户
      当   提交 /api/inbox
      那么 返回 401 且 body.error = "unauthenticated"
      断言 api/tests/inbox.spec.ts::rejects_anonymous

AC-2  给定 一段 200 字描述
      当   提交后轮询 /api/inbox?limit=1
      那么 首条记录 content 完全相等，created_at 与提交时间差 < 3s
      断言 api/tests/inbox.spec.ts::creates_item_at_head
```

质量线：

- **可判定**：两个人独立判断会得出同样结论。"友好地提示"不合格，"显示『网络异常，请重试』"合格
- **含失败路径**：至少一条空值 / 边界 / 异常。只写 happy path 的 spec 是半个 spec
- **不含实现**：不写"用 Redis 缓存"。实现决策放"边界与接口"，或者不写
- **数量** 3-8 条。少于 3 条说明没想清楚，多于 8 条说明片切大了

### 5. 非功能约束

三行，强制写，每行必须可测。这一节存在的理由是：AC 只写外部可观测的**行为**，性能、安全、可观测性会被系统性排除——而这恰恰是 agent 生成代码时默认不做的东西。

- **性能**：`上传 10MB 文件，p95 < 2s` / `超过 10MB 返回 413 且不落盘`
- **安全**：`未授权访问返回 403` / `日志中不出现 token 明文`
- **可观测**：`每条失败请求产生一条 error 级日志，含 request_id`

写"性能要好"等于没写。

### 6. 边界与接口

五行，强制写：

- **拥有**：这片负责的数据、模块、页面
- **消费**：依赖谁的输出，契约是什么（字段、格式、错误码）
- **绝不碰**：明确不修改的部分
- **共享契约**：如果要动公共类型 / API schema，写清"只追加字段，不改已有字段"，并注明契约 owner 切片必须先于所有消费者完成
- **落点**：新增或修改的模块路径、测试放哪、参照哪个已有测试

最后一行容易漏，代价很大：不写落点，每份 spec 各造一套目录和命名，五片之后代码库里有三种 `utils`。

只写"绝不碰"挡不住并行冲突——两个 agent 各自新建 `utils/date.ts` 和 `lib/format.ts`，功能重复但谁都没越界。共享契约那一行是为这个准备的。

### 7. 依赖

被哪些切片阻塞。没有就写"无，可立即开始"。

### 8. 验收方式

**必须是一条执行者自己能跑的命令**，附期望输出片段：

```
$ pnpm test specs/001
✓ rejects_anonymous
✓ creates_item_at_head
2 passed
```

需要点界面才能验的，先写一条 e2e，验收方式改成跑这条 e2e。人眼操作只能作为附注——没有浏览器工具的 agent 遇到"打开 /inbox 点一下"只有两个选择：谎称验过，或者跳过。前者更常见。

### 9. 风险与开放问题

开放问题只能出现在这里，**不能出现在验收标准里**。AC 里出现 TBD，这份 spec 就没写完。

会阻塞实现的开放问题，说明这片该改成 spike。

## 滚动式细化

只详写到**接下来两三片**，后面的在 `_index.md` 里留一行标题。

这也是文档腐化的解药——文档越少、越短、越靠近代码，越不容易过期。

## 自检清单

- [ ] 这片能独立演示，不需要整个产品跑起来
- [ ] 每条 AC 都有断言点和字面量期望值，没有 TBD、没有"正常""友好""合理"
- [ ] 至少一条失败路径
- [ ] 非功能三行写全，且可测
- [ ] 边界五行写全（拥有 / 消费 / 绝不碰 / 共享契约 / 落点）
- [ ] 画像在文内复述过，不是只给链接
- [ ] 验收方式是命令，不是"打开浏览器点一下"
- [ ] 一个没有对话上下文的执行者，只读这份文件就能开工
