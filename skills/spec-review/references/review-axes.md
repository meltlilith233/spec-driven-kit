# 三个轴的细则

起 sub-agent 时，把对应整段贴进它的 prompt——它读不到这个文件。

**两份 brief 都是填空模板，四处必须替换成真实值**：固定点、diff 命令、spec 路径、规范来源。把占位符原样递过去，sub-agent 要么忽略它，要么自己编一套标准。

---

## Spec 轴

### 报什么

| 类型 | 定义 | 例子 |
|---|---|---|
| **缺失** | spec 要求了，diff 里没有 | AC-4 要求"可编辑后确认"，只有确认没有编辑 |
| **部分** | 做了，但没覆盖 AC 的全部条件 | AC-2 写了失败路径，代码只处理了成功 |
| **膨胀** | diff 里有，spec 没要求 | 顺手加了导出功能 |
| **实现错** | 看着实现了，方式不对 | 分页做了，但按 id 排不是按时间 |

非功能约束（性能 / 安全 / 可观测）也算在内——它们最常被写进 spec 然后在实现里蒸发。日志里打出 token、上传没有大小限制、失败请求没有 request_id，都是 Spec 轴的缺失，不是 Standards 轴的问题。

### brief 模板

贴之前替换 `<fixed>` 和 `<spec-path>`。

```
你在审一份 diff 是否忠实实现了指定 spec。你的判断只关乎"做的是不是 spec 要的"，
不评价代码风格——那由另一个人负责。

固定点：<fixed>
diff：git diff <fixed>...HEAD
相关提交：git log <fixed>..HEAD --oneline
spec：<spec-path>（先完整读一遍，注意每条 AC 的断言字段和"不做"一节）

报四类问题，每条必须引 spec 原文：
(a) 缺失：spec 要求但 diff 里没有的
(b) 部分：只实现了一部分，说明缺哪个条件
(c) 膨胀：diff 里有但 spec 没要求的
(d) 实现错：实现了，但方式与 spec 不符

非功能约束（性能 / 安全 / 可观测）的缺失，算 (a) 或 (b)，不要归到风格问题。

不确定的标"待确认"，不要猜。400 字以内。
```

## Standards 轴

### 先找仓库自己的规范

按顺序找，找到就都要：

1. `CODING_STANDARDS.md`、`CONTRIBUTING.md`、`AGENTS.md`、`CLAUDE.md`
2. `docs/` 下与代码风格、架构决策相关的文档
3. 配置里体现的约定：lint 配置、tsconfig 严格度、目录结构

仓库有文档化规范时，**规范优先于下面的 baseline**——规范认可的做法，baseline 就不该再报。

### Brief 模板

baseline 整表内联在模板里，复制时不要拆开——sub-agent 只有这一处能拿到它。

```
你在审一份 diff 是否符合本仓库的编码规范。你只评价代码质量与一致性，
不判断功能是否符合需求——那由另一个人负责。

固定点：<fixed>
diff：git diff <fixed>...HEAD
相关提交：git log <fixed>..HEAD --oneline
仓库规范来源：<规范文件列表>

报两类，每条引 diff 里的具体行或 hunk：
(a) 违反仓库文档化规范的：引用规范原文。这类算硬违规。
(b) baseline 里的坏味道：点名 + 引 hunk。这类只算判断，写"可能的 X"。

下面是 baseline。仓库文档化规范与之冲突时，以仓库为准：

| 坏味道 | 什么算 | 怎么改 |
|---|---|---|
| 神秘命名 | 名字看不出做什么或装什么 | 改名；改不出来说明设计本身糊 |
| 重复代码 | 同一段逻辑形状出现在多处 | 抽出共同形状，两边调用 |
| 依恋情结 | 方法频繁取用另一个对象的数据 | 把方法搬到数据那边 |
| 数据泥团 | 几个字段总是一起出现 | 合成一个类型 |
| 基本类型偏执 | 用 string/number 代替领域概念 | 给概念一个小类型 |
| 重复的 switch | 对同一类型反复写 if/switch 级联 | 换成多态或一张共享映射 |
| 霰弹式修改 | 一个逻辑改动要散着改很多文件 | 把一起变的东西聚到一处 |
| 发散式变化 | 一个文件为多个不相关的原因被改 | 拆到各自只为一种原因变 |
| 夸夸其谈通用性 | 为 spec 里没有的需求加了抽象/参数/钩子 | 删掉，等真有需要再说 |
| 过长的消息链 | a.b().c().d() 一路点下去 | 在第一个对象上加方法挡住 |
| 中间人 | 一个类/函数大部分只是在转发 | 砍掉，直接调真正的目标 |
| 被拒绝的遗赠 | 子类忽略或覆盖了大部分继承来的东西 | 去掉继承，改组合 |

lint、类型检查、formatter 已经强制的不要报。400 字以内。
```

**夸夸其谈通用性**在 AI 生成的代码里出现率最高：为一个只用到一次的接口写了策略模式、配置项、插件钩子。看到就报。

## 证据轴

不用 sub-agent。三条命令加一次核对，全部在本体做。

### 前置检查

**spec 里有「回填」表吗？没有就整轴记「不适用」，不参与结论。**

只用过 `spec-implement`、没走过 `spec-mvp` 的项目，本来就没有伪造清单。照着"有清单"的规则去核，会造出一个假警报——比漏报更浪费时间。

### 三条命令

```bash
# 1. 红绿是不是成对发生的
git log --oneline <fixed>..HEAD
#    找 test(SPEC-003 AC-2) 后面跟一个 feat(SPEC-003 AC-2)

# 2. 伪造标记和清单对不对得上（不要限定目录）
git grep -n "MVP-FAKE"
#    逐条比：伪造清单的每一行，至少命中一处

# 3. 回填表有没有真的写进文件
git diff --stat docs/specs/
```

第四步逐条核回填表：

```
AC-2 → api/tests/inbox.spec.ts::creates_item_at_head
       ↑ 文件在不在       ↑ 用例名在不在       ↑ 跑一次绿不绿
```

### 判据（三态）

| 情况 | 判 |
|---|---|
| 回填表与代码对得上、成对提交齐 | **通过** |
| 查不到用例 / 表是空的 / 有伪造没标记 | **不通过** |
| squash、保护分支、非 git 仓库 | 看回填表里的红输出，有则通过 |
| spec 没有回填表 | **不适用**，不参与结论 |

两个最容易判错的地方：

- **`MVP-FAKE` 比"有没有"，不比总数。** 一行伪造清单可能落在好几处标记上，数量对不上是正常的。
- **`grep` 不要写死 `src/`。** Python 仓库可能没有这个目录，写死了必然零输出，然后判"有伪造没标记"——这是假警报最常见的来源。

这一轴不给"部分通过"。要么有物证，要么没有。

## 报告格式

```
## 降级说明
（无 spec / 无固定点时才写这一节，否则删掉）

## Spec 轴
（按四类分组，每条引 spec 原文）

## Standards 轴
（硬违规 / 判断项 分两段）

## 证据
（四行：成对提交 / MVP-FAKE 逐条 / 回填表 / 判据结论）

## 小结
Spec x 条，Standards y 条，证据 通过|不通过|不适用
每块最严重的一条（跨块不排名）
```
