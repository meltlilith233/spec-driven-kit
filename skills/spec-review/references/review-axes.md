# 三个轴的细则

起 sub-agent 时，把对应整段贴进它的 prompt——它读不到这个文件。

---

## Spec 轴

### 报什么

| 类型 | 定义 | 例子 |
|---|---|---|
| **缺失** | spec 要求了，diff 里没有 | AC-4 要求"可编辑后确认"，只有确认没有编辑 |
| **部分** | 做了，但没覆盖 AC 的全部条件 | AC-2 写了失败路径，代码只处理了成功 |
| **膨胀** | diff 里有，spec 没要求 | 顺手加了导出功能 |
| **实现错** | 看着实现了，方式不对 | 分页做了，但按 id 排不是按时间 |

非功能约束（性能/安全/可观测）也算在内——它们常常被写进 spec 然后在实现里蒸发。日志里打出 token、上传没有大小限制，都是 Spec 轴的缺失，不是 Standards 轴的问题。

### brief 模板

> 你在审一份 diff 是否忠实实现了指定 spec。
>
> diff：`git diff <fixed>...HEAD`；相关提交：`git log <fixed>..HEAD --oneline`
> spec：`<path>`（先完整读一遍）
>
> 报四类问题，每条必须引 spec 原文：
> (a) spec 要求但 diff 里缺失的
> (b) 只实现了一部分的（说明缺哪个条件）
> (c) diff 里有但 spec 没要求的
> (d) 实现了但方式与 spec 不符的
>
> 不确定的标"待确认"，不要猜。400 字以内。

## Standards 轴

### 先找仓库自己的规范

按顺序找，找到就都要：

1. `CODING_STANDARDS.md`、`CONTRIBUTING.md`、`AGENTS.md`、`CLAUDE.md`
2. `docs/` 下与代码风格、架构决策相关的文档
3. 配置里体现的约定：lint 配置、tsconfig 严格度、目录结构

仓库有文档化规范时，**规范优先于下面的 baseline**——规范认可的做法，baseline 就不该再报。

### Baseline（仓库什么都没写时用）

这些是判断项，不是硬违规。报的时候写"可能的 X"，不要写成"违反规定"。

| 坏味道 | 什么算 | 怎么改 |
|---|---|---|
| 神秘命名 | 名字看不出做什么或装什么 | 改名；改不出来说明设计本身糊 |
| 重复代码 | 同一段逻辑形状出现在多处 | 抽出共同形状，两边调用 |
| 依恋情结 | 方法频繁取用另一个对象的数据 | 把方法搬到数据那边 |
| 数据泥团 | 几个字段总是一起出现 | 合成一个类型 |
| 基本类型偏执 | 用 string/number 代替领域概念 | 给概念一个小类型 |
| 重复的 switch | 对同一类型反复写 if/switch 级联 | 换成多态或一张共享映射 |
| 霰弹式修改 | 一个逻辑改动要散着改很多文件 | 把一起变的东西聚到一处 |
| 发散式变化 | 一个文件为多个不相关的原因被改 | 拆到各自只为一种原因变 |
| 夸夸其谈通用性 | 为 spec 里没有的需求加了抽象/参数/钩子 | 删掉，等真有需要再说 |
| 过长的消息链 | `a.b().c().d()` 一路点下去 | 在第一个对象上加一个方法挡住 |
| 中间人 | 一个类/函数大部分只是在转发 | 砍掉，直接调真正的目标 |
| 被拒绝的遗赠 | 子类忽略或覆盖了大部分继承来的东西 | 去掉继承，改组合 |

**夸夸其谈通用性**在 AI 生成的代码里出现率最高：为一个只用到一次的接口写了策略模式、配置项、插件钩子。看到就报。

### brief 模板

> 你在审一份 diff 是否符合本仓库的编码规范。
>
> diff：`git diff <fixed>...HEAD`；相关提交：`git log <fixed>..HEAD --oneline`
> 仓库规范来源：`<列出找到的文件>`
>
> 报两类，每条引 diff 里的具体行或 hunk：
> (a) 违反仓库文档化规范的：引用规范原文，这类算硬违规
> (b) baseline 里的坏味道：点名 + 引 hunk，这类只算判断
>
> 下面是 baseline，仓库规范与之冲突时以仓库为准：
> `<贴上面的表格>`
>
> 工具（lint、类型检查、formatter）已经强制的不要报。400 字以内。

## 证据轴

不用 sub-agent。三条命令加一次核对，全部在本体做。

```bash
# 1. 红绿是不是成对发生的
git log --oneline <fixed>..HEAD
#    看有没有 test(<scope>): AC-N 后面跟一个 feat(<scope>): AC-N

# 2. 伪造标记和清单对不对得上
grep -rn "MVP-FAKE" src/
#    数量要和 MVP spec 伪造清单的行数一致，差集要能解释

# 3. 文档回填有没有真的发生
git diff --stat docs/specs/
```

第四步是逐条核对映射表：

```
AC-2 → api/tests/inbox.spec.ts::creates_item_at_head
       ↑ 文件在不在       ↑ 用例名在不在       ↑ 跑一次绿不绿
```

### 判据

| 结果 | 含义 |
|---|---|
| 全部对得上 | 证据成立 |
| 映射表里有查不到的用例 | 回填是编的，或者测试后来被删了 |
| 没有成对提交 | 双提交没执行（非 git 仓库除外，那要看红输出有没有留在产物里） |
| `MVP-FAKE` 少于清单行数 | 有伪造没标记，半年后没人找得到 |

这一轴不给"部分通过"。要么有物证，要么没有。

## 报告格式

```
## Spec 轴
（按四类分组，每条引 spec 原文）

## Standards 轴
（硬违规 / 判断项 分两段）

## 证据
（四行表格：成对提交 / MVP-FAKE 对账 / 文档回填 / 映射表可跑）

## 小结
Spec x 条，Standards y 条，证据 通过|不通过
每块最严重的一条（跨块不排名）
```
