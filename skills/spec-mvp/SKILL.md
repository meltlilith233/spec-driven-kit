# Spec to MVP

把一份 spec 收敛成最小可验证版本：保住要验证的假设，砍掉其他一切。

判断标准不是功能多少，是**花最少的代价，最快地知道这个判断是错的**。

做完如果对"该不该继续"的答案没变得更确定，那它不是 MVP，只是做得比较糙的完整版。

## 不可伪造清单

支付计费、身份认证、第二个用户之后的授权、数据删除、个人数据、合规约束。

命中就是**不做 MVP，直接走完整实现**——这是判定，不是提问。

## 三步

**1. 定假设。** 一句话，可证伪。从风险节、用户故事"以便"的后半句、或"哪几条 AC 不成立整件事就没意义"里挖。

收益确定性的需求（流程缩短、性能、迁移、合规）本来就没有假设，改写"跑完要回答的一个问题"。别硬编——编出来的假命题会让你砍错东西砍得理直气壮。

**2. 分成三类。** 每条 AC 问三个问题：没有它假设还能验吗（**保留**）；能用假数据、硬编码、手动步骤替代吗（**伪造**）；都不成立（**砍掉**）。

逐条写进三类判定表，覆盖原 spec 的全部 AC。审阅者唯一能复核的就是"为什么这条被砍"。

伪造是主力，比删省得多——但**假设的核心载体不可伪造**。如果那一环被硬编码或换成 fixture，跑完得到的绿灯不构成证据。这时该判"砍"，或者承认这个假设要完整实现才验得了。

**3. 定完成与成本。** 判定协议先写，事后解释的阈值等于没有。成本上限写成三个数字，不是时间：

```
≤ 3 文件 / ≤ 200 行（不含测试）/ ≤ 4 条 AC
```

超了回去继续砍，不许延期。"一个下午"给不了任何约束。

## 交付

交给 `spec-implement`，并把状态推到 `ready`。它跑完会改成 `awaiting-verdict`。

## 判定

这是本 skill 的第二个入口，不是收尾附注。

**触发**：MVP spec 里写的"什么时候收证据"到了，或者用户说"结果出来了"。

**动作**：读证据 → 对照阈值 → 写一句结论 → 状态改 `done` 或 `superseded`，在 `_index` 记一行结论。

**不成立就停，不要加功能去救。** 那是沉没成本，不是学习。想重开一轮就新建一份 MVP spec，不在原文件上改阈值。

## 边界

自己可以做：砍功能、定伪造方案、写 MVP spec、判定。

必须先问：伪造范围超出清单、放宽成本上限、改判定阈值、把砍掉的东西加回来。
