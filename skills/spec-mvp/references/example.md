# 一个完整的收缩示例

## 原 spec：语音需求转任务（SPEC-007）

> **目标**：用户可以录一段语音，系统转文字并自动拆成 3-5 条任务建议，确认后写入任务列表。

验收标准（原样，9 条）：

- AC-1 未登录访问返回 401
- AC-2 上传 ≤ 60s 的音频，20 秒内返回转写文本
- AC-3 转写文本被拆成 3-5 条任务，每条含标题与截止日期（若有）
- AC-4 用户可以编辑任意一条建议后确认
- AC-5 确认后任务写入列表，出现在首条
- AC-6 音频格式不支持时返回 415
- AC-7 转写失败的录音保留 7 天可重试
- AC-8 每条任务记录创建者与来源音频 id
- AC-9 列表支持按创建时间倒序分页

## 收成 MVP

### 假设

> **真实需求的口述，机器拆完只需要改 1-2 个字就能直接用。**

这句话一旦不成立，整件事就没意义——如果每次都要把 3 条建议重写成 5 条不同的，那"自动拆分"只是个昂贵的输入法。而"能不能转文字"是已知的，不需要验证。

**这句话必须是能自己验的。** 最初的写法是"用户愿意直接确认机器拆出来的任务"——但证据是"我自己用 5 天"，n=1 的自己证伪不了关于"用户"的命题。要么改成找 3 个真人，要么把命题收到自己能验的范围。这里选后者：验证的是产出质量够不够用，不是别人会不会采用。采用与否，等质量过关了再说。

它和"用户需要语音记需求"的区别：后者几乎一定成立，验证它是浪费。

### 三档划分

| AC | 判断 | 理由 |
|---|---|---|
| AC-1 未登录 401 | **砍** | MVP 只给自己用，没有登录 |
| AC-2 20 秒内返回 | **保留**（放宽） | 但阈值从 20s 放到 60s——速度不是这个假设的一部分 |
| AC-3 拆成 3-5 条 | **保留** | 假设的核心载体 |
| AC-4 可编辑后确认 | **保留** | 编辑率正是要测的数据。删掉它，你就测不出"用户愿不愿意接受" |
| AC-5 写入列表 | **保留**（简化） | 写上就行，不要求"出现在首条" |
| AC-6 415 | **砍** | 自己录的音频，格式自己定 |
| AC-7 失败保留 7 天 | **伪造** | 失败就重录，不做留存 |
| AC-8 记录创建者 | **伪造** | user_id 写死 |
| AC-9 分页 | **砍** | 十来个任务不需要分页 |

结果：9 条 → 4 条。

### 伪造清单

| 真东西 | MVP 替代 | 上线前必须换成 |
|---|---|---|
| 用户系统 | 写死 `user_id = "me"` | 真登录 |
| 数据库 | `data/tasks.json` | Postgres |
| 转写服务 | 直接用现成 API，不做重试与降级 | 加重试、超时、降级 |
| 音频存储 | 存本地 `tmp/`，不清理 | 对象存储 + 生命周期 |
| 任务写入 | 直接 append 到 JSON | 带事务的写入 |

### 砍掉的（后续版本）

音频格式校验、失败重试与留存、分页、来源追踪、多人协作。

### 完成定义

- 方式：自己用 5 天，每天至少录 3 条真实需求（不是编的场景）
- 记录：每次确认前，记下改了几条建议里的几个字（0 = 完全接受）
- 什么时候收：第 5 天晚上
- 谁判定：你自己。不成立就停，别加功能去救
- 成立：≥60% 的录音是"零修改"或"改 1-2 个字"
- 不成立：多数要整条重写，或者录了两天就不想再录了

阈值必须是这六行，不是一句"看情况"。少一行，五天后你会给自己找理由。

### 成本上限

**≤ 3 个文件 / ≤ 200 行（不含测试）/ ≤ 4 条 AC**（约两个下午）。

超了就说明伪造得还不够狠——回去看伪造清单，还有哪里能假。

## 做错了会是什么样

同一份 spec，另一种"MVP"：

- 保留全部 9 条 AC（"都要的，只是先做简单点"）
- 建了用户表（"反正迟早要"）
- 加了音频格式校验（"不然体验不好"）
- 搭了任务列表的分页组件（"顺手"）

产物叫 MVP，实际是三周工作量，而且它验证的仍然是"语音能不能转文字"——一个从来不是风险的问题。

它和上面那版的差别不在功能多少，在于上面那版跑完会拿到一个能回答"继续还是停"的数字，这版跑完只会拿到一个能用的东西。

**判断依据只有一条**：这个版本跑完，你会不会因为它的结果而改变下一步的决定。会，是 MVP；不会，是缩小版产品。
